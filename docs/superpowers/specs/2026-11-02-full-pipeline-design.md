# One-button pipeline: upload everything, get a rebuilt plan

Status: design, awaiting Jonathan's approval. Nothing here is built.

## 1. Intent

Today HealthForecast is a set of separate steps, and only patient arrivals can
be uploaded. A person must load curated CSVs, press Merge, press Forecast, press
Optimise, and hope the results agree. Inventory and rostering run on files
bundled with the app.

Jonathan wants the whole journey in one place. From the upload page, a user
drops in all the files: the raw monthly patient registers, external factors,
inventory and scheduling. One button then runs transformation, consolidation,
analysis, forecasting, the inventory and scheduling optimisation, and rebuilds
the recommendations. The point is to demonstrate the full pipeline working end
to end, on the thesis work, in the real app.

Inventory and scheduling data stay **simulated**. No real hospital inventory or
roster data exists anywhere in the three source folders. The simulated data
becomes CSV files that go through the real upload path, purely to demonstrate
the pipeline. Real files can replace them later without code changes.

## 2. Goals

1. One page accepts every file type: raw `.xlsx` registers and CSVs.
2. One button runs every stage in order, with visible progress per stage.
3. Raw registers go through the real transformation and yield the same result
   as the offline pipeline, proven by comparison with the existing `pure_*.csv`.
4. Inventory and scheduling come from uploaded files, and every page that shows
   them reads those files.
5. After a run, every page, the AI assistant and the recommendations describe
   the same data. Nothing stale survives.
6. It runs and is verified locally: backend and frontend started, files really
   uploaded through the browser, results checked.

## 3. Non-goals

- Deployment to Render. `main` and the live site do not change. A separate
  decision follows the local demo.
- Real inventory or roster data, or accepting arbitrary hospital formats.
- Retraining the thesis models, or loading their `.pkl` files. No torch, no
  xgboost, no pmdarima. The app's forecasting engines keep retraining on G1,
  as they do today.
- Fixing the known data-quality issues in the offline pipeline (section 11).
  The port must reproduce the current output first, or it cannot be proven.
- Persistence across restarts, per-user workspaces, and a job queue service.
- The AnyLogic work, thesis figures, the 10,000-sample bootstrap, SHAP, and the
  30-seed sensitivity sweep. These are too slow or thesis-specific.

## 4. Anti-goals: a failure even if it technically works

- Simulated inventory or staffing shown as if it were real hospital data.
- Patient names or hospital numbers reaching a log, a response, a temp file or
  a report.
- A chart or AI answer built on the previous upload.
- A cross-file finding stated as a discovery when the simulator built it in
  (section 7).
- An accuracy percentage or MAPE appearing outside the admin view.
- The run silently changing the adopted reorder policy family.

## 6. The files

### 6.1 Patient and external files

| File | Format | Required | Notes |
|---|---|---|---|
| `Casualty_Daily_Register_YYYY_MM.xlsx` | Raw Excel, any number | See below | Filename gives the month. Hospital originals with other names are rejected with a clear message |

At least one route must supply arrivals: raw registers, or the pure CSVs, or

Principle: **the files hold what a hospital would have**. Master lists, stock
movements, a payroll or timesheet summary, a shift log. They do not hold the
simulator's results: `total_stockout_cost_zar`, `service_level_achieved` and
similar are computed by the app. This is what makes the upload a pipeline rather
than a file swap.

`staff_kpis.csv` and `supply_kpis.csv` are 30-seed simulation statistics with no
real-world equivalent, so they are not uploaded. In uploaded mode `load()`
returns an empty frame and the `ci` block is empty. Staff and Supply pages must
render cleanly without it.

`data_origin` is required in `inventory_items.csv` and `staff_list.csv`, with
values `simulated` or `real`. It survives renaming a file, and it drives the
banner in section 9.

All data covers 2025-01-01 to 2026-01-31, the last 396 days of the real arrivals
history, so the dates line up without shifting.

### 6.3 Deriving what the engines need

New `api/core/ops_derive.py` turns the uploaded files into the seven table names
`simulation_data.load()` already serves. A new `publish(frames)` in
`core/simulation_data.py` holds them in an `_UPLOADED` dict checked first by
`load()`. **No call site changes.** That is the seam: about 15 callers across
`routers/optimization.py`, `supply.py` and `staff.py` keep working untouched.

- `supply_items` = `inventory_items` plus per-item figures from the movements:
  total, mean and sd of consumption, CV, stockout events and units, orders
  placed, average stock, service level, and holding, ordering, stockout and
  expiry costs, inventory value, `observed_days`.
- `supply_panel` = `inventory_movements`, unchanged.
- `staff_members` = rows of `staff_list` with `is_vacant` false.
- `staff_shifts` = `shift_log`, unchanged. `staff_daily` = `staffing_daily`.

Round-trip check: deriving from the demo pack should reproduce the bundled
`supply_items.csv`. The cost columns may not match exactly, because the
simulator accrues them day by day. The builder documents any difference and how
large it is, and must not paper over it.

How the uploaded cost inputs reach the engines:

- **Ordering cost and stockout penalty** already flow through. The default
  `dynamic` path backs them out of totals in `_item_cost_params`
  (`optimization_engine.py:455-468`), and `ops_derive` builds those totals from
  the uploaded values. The `s_q` and `r_s` paths read `ordering_cost_zar` directly
  at line 1544; that column now exists, where today it falls back to R50.
- **Holding rate** is hard-coded today: 0.25 in the planner and tuner, 0.22 in the
  supply ladder. Change these to read `holding_cost_rate_per_year` from the item
  when present, and keep the existing constants otherwise.

Default mode, with no upload, keeps today's numbers. In uploaded mode supply
results may differ from the live app because of these real inputs, and that is
correct. The builder records the size of the difference.

## 7. Cross-file checks and honest analysis

Stage 0 and stage 3 check that the files agree:

- `staffing_daily.total_arrivals` against G1 for each shared date. A mismatch is
  a warning naming the count of days and the largest gap.
- Every `item_id` in movements exists in items, and vice versa.
- Date coverage overlaps between arrivals, movements and shifts.
- Shift names are Day, Evening, Night. `Professional Nurse` is present, because
  the solver matches that exact string.

**The honesty rule.** Simulated consumption and staffing were generated from
real arrivals. Any strong link between arrivals and consumption is therefore
built in, not discovered. Cross-domain results carry a label when
`data_origin` is `simulated`: "This relationship was built into the simulated
data, so it shows the pipeline working, not a finding about the hospital."

## 8. The run

### 8.0 Raw files are transformed as they arrive

Raw Excel files are **not** held until Run. The 81 workbooks total 383MB, which
cannot be held in RAM on a 512MB server, and holding them would keep patient names
in memory for no benefit. Instead:

- The browser sends one workbook at a time. The request transforms that month in a
  worker thread and answers with a receipt (or a reason it failed), then the next
  file goes. The raw bytes are gone before the next file starts.
- Only the month's aggregates are kept, in a staged store, keyed by month.
- The tab must stay open while raw files upload, as with any upload. Files already
  done are kept if it closes.

Staging rules, which make a second run cheap:

- Staged months and staged CSVs **stay staged after a run**. Run 2 needs only the
  file that changed. A re-uploaded month or CSV replaces the staged one.
- A Clear button empties staging. All of it is in RAM, so a restart empties it too,
  and the page says so.
- A **Download transformed CSVs** button gives the four pure tables, which the
  existing slots accept. This avoids repeating a 20-minute upload after a restart,
  and it is how the Quick demo route gets its history files.

### 8.0.1 The job

`POST /api/pipeline/run` starts one background thread. `GET /api/pipeline/status`
is polled by the page. One job at a time; a second run gets HTTP 409. Thin
router `routers/pipeline.py`; logic in `api/core/pipeline/`. It requires
`data:write`. A failed stage stops the run, marks later stages skipped, and
leaves previous results cleared rather than half-replaced, with the reason shown.

| # | Stage | Does | Reuses |
|---|---|---|---|
| 0 | Check | Files present, columns correct, cross-file checks. Blocks on errors, carries warnings | `core/datasets.py` |
| 1 | Transform | Merge the already-transformed months (section 8.0) into the four pure tables. Skipped, and shown as skipped, when there are none | New `core/transform/` |
| 2 | Operations | Section 6.3, then `publish` | New `ops_derive.py` |
| 3 | Consolidate | Build G1 to G4 sequentially, then a new daily operations table: date, arrivals, required and staffed nurses, locum hours, consumption units, stockout units, stock value | `core/joins.py` |
| 4 | Analyse | Explore pipeline over G1 to G4, plus new analyzers (below) | `core/explore/` |
| 5 | Forecast | Total ED with a rolling-origin backtest, published to `/last`, so buffers use the validated error. Then all seven specialties, no backtest, into a separate keyed store, so they never replace Total ED | `core/forecasting.py`, `core/validation.py` |
| 6 | Optimise | Lawful roster, then the weekly supply plan within the adopted family, published to `/last`. Then the policy and strategy evidence ladders | `core/optimization_engine.py` |
| 7 | Recommend | Generate the action list once and store it with the data version | `api/ai/actions.py` |

Stage 1 detail: transformed months replace the same months in any uploaded pure
history. The months that would be replaced are listed before the run starts, so
nothing is overwritten silently. Failed months are absent and listed; the run
stops before stage 2 only if no arrivals remain. The checks from
`scripts/validate_pure_datasets.py` then run and go in the receipt.

Stage 4 new analyzers, one file each, per the plug-in pattern:
- Arrivals against consumption; arrivals against nurses required; stockout days
  against busy days. Labelled per section 7.
- Thesis checks missing from Explore. The builder first maps the steps in
  `dataAnalysis/scripts/run_pure_*.py` to the existing analyzers, then adds only
  those missing and quick to compute: VMR, Kruskal-Wallis for day of week and
  month, ACF. Verdicts must come from the computed values. The thesis scripts
  print some verdicts unconditionally (`run_pure_daily_phase2.py:247`,
  `run_pure_daily_phase6_8_9.py:278`), and that must not be copied.

Stage 6 and the standing policy: the run **recommends** a reorder family through
the evidence ladder but never adopts it. Adoption remains the explicit
`PUT /api/optimization/policy`. Naive stays a benchmark and oracle stays hidden.

Stage 6 and the rostering ladder: in uploaded mode `compare_staff_strategies` gets
`mean_arrivals` from G1 and the pool size from the staff list, so it responds to
the data. Its R180 hourly rate and thesis forecast-error constant stay, and the
card says so: "Illustrative rates and error, from the thesis." Default mode with
no upload keeps the Chapter 7 calibrated numbers exactly.

Stage 7 and no AI key: the stage ends amber with "Recommendations need an AI key".
The run still completes, because stages 1 to 6 stand alone. Action Center reads
the stored list and shows when it was built. Its existing on-demand path stays
as the fallback only when no stored list exists.

### 8.1 Invalidation

New `core/data_version.py` holds one counter and `invalidate_all()`, called at
the start of a run. It clears every result cache: `_LAST` in the engine,
`_LAST_RUN`, `_LAST_TUNE`, `_LAST_COMPARE`, `_LAST_SWEEP`, `_LAST_STRATEGY`,
`_FC_CACHE`, `_ENGINE_CACHE`, `_VALIDATION_CACHE`, the stored actions.
The adopted **family** in `_POLICY_STATE` is kept, because it is a standing choice.
Its `params_by_item` and `tuned_at` are reset to textbook values, because they were
fitted on the old data, and the run receipt says: "Tuned reorder settings were reset
because the data changed. Re-tune on the Optimization page." The run does not retune
on its own. The default `dynamic` family does not use these parameters.

Each cache owner registers a clear function, so a future cache cannot be
forgotten by editing one list. Every `/last` payload carries `data_version`.
The specialty store from stage 5 is cleared the same way, and `Task2Forecast.jsx`
offers its results through a Load button, per Plan C.

### 8.2 Things that must change for this to be true

- `Dashboard.jsx:32` POSTs `/forecast/run` on load. It breaks Plan C and would
  recompute behind a run. It reads `/forecast/last` instead.
- `/forecast/run` fits models on the event loop. The job calls engines from its
  own thread; the endpoint runs in a thread pool.
- `optimization.py:183` returns a bare `None` where a pair is unpacked.
- `OBSERVED_PERIOD_DAYS` 396 comes from `observed_days` on each item.
- `STAFF_N_ACTIVE` 23 comes from the staff list. `n_posts` 30 in `staff.py:130`
  comes from `staff_list` row count.
- Optimisation silently falls back to demo data if G1 is missing
  (`optimization.py:116`). Within a run, that is a failure, never a fallback.
- `core/bootstrap.py` only fills G1 when empty, and never overwrites a run.

## 9. The user experience

Data Hub stays the upload page.

- One drop zone. Files are classified by name and columns into four groups:
  patient registers, external factors, inventory, scheduling. A checklist shows
  what is present, what is missing, and any problem per file.
- Excel files upload and transform one at a time as soon as they are dropped, with
  a progress count and a per-file receipt. The tab stays open for this part.
- **Run full pipeline** is enabled once required files are present. It shows the
  months that would be replaced, if any.
- A stage tracker shows the eight stages, each with status, time taken and a
  one-line receipt, such as "80 months, 138,287 arrivals, no patient identifiers
  kept". Once Run is pressed, the page can be left and returned to, and the run
  continues.
- On completion, a summary with links: Explore, Forecast, Staffing, Supply,
  Optimization, Action Center.
- The existing per-slot tiles move under an Advanced section, unchanged.
- Staged files are held in RAM until cleared or the server restarts, and the page
  says so.

Pages showing simulated inputs (Staffing, Supply, Optimization, Action Center)
show a banner while `data_origin` is `simulated`: "Inventory and staffing are
simulated demonstration data." A header note states the data source: "Uploaded
run 3, 2 Nov 2026 14:05" or "Default data". After a restart it reverts to
default and says so.

The AI assistant keeps its read-only tools. Its hard-coded "SIMULATED" source
strings (`ai/tools.py:210,238`) become driven by `data_origin`.

## 10. Transformation port

Package `api/core/transform/`, ported from
`healthforecast_pipeline/run_pipeline.py`, `scripts/extract_clinical_reasons.py`
and `src/purify.py`. The legacy `pipeline.py` and `src/extract.py` are not used.

- **Extraction logic is copied, not rewritten.** Only input and output change:
  each function takes a loaded sheet, year and month, and returns DataFrames.
  Today's code needs a `.name` on the file, and passes CSVs on disk between
  phases 2c and 5 to 7.
- **Each workbook is read once**, not three times as today.
- **Reader:** `openpyxl` is added to `requirements.txt`. The builder should also
  test `python-calamine`, which may be far faster. Use it only if it produces an
  identical cell grid across all 81 files, and otherwise keep `openpyxl`.

**Privacy.** Raw files contain patient names, hospital numbers and staff names.

- Bytes arrive as a raw request body, one file per request, read into memory
  with a size cap. Multipart is not used, because Starlette spools uploads over
  1MB to a temp file, which would break the rule that hospital files are never
  written to disk.
- The bytes and worksheet are held only while extracting that one month, then
  deleted, before the response returns (section 8.0).
- Only numeric aggregates leave the extractor. Patient-level rows, names and cell
  values never appear in a log, an exception message or a response. Error text
  names only the file and the phase.
- Add `api/tests` coverage: a synthetic workbook with fake identifiers must
  produce output containing none of them.

**Proof of equivalence.** A test gated on a `RAW_REGISTER_DIR` environment
variable runs the port over the raw files and compares with
`output/pure/pure_*.csv`, month by month, for an exact match. Raw files are never
committed. The default test suite uses the synthetic workbook. The port is not
considered done until all 80 months match, or each difference is explained in
writing.

## 11. Known issues carried forward, and shown

The offline pipeline has problems that this work reproduces deliberately. They
go in the run receipt as warnings where detectable, and in a follow-up list.

- `pure_hourly_clinical` is daily values repeated 24 times, not hourly.
- Purify drops `_all` and `total_` columns, so 36 of 85 clinical columns are zero
  before 2023-04.
- 14 of the 17 zero-arrival days fall in July 2020 and November 2022, and may be
  missing data.
- Untimed patients drop out of the hourly totals.
- January 2026 is all flagged as school holiday; `days_to_next_holiday` sticks.

One exception, because it is new behaviour: a failed clinical extraction today
becomes silent zeros (`src/purify.py:89`). In the port it marks that month failed.

`docs/data-upload-plan.md` claims 5 to 10 seconds per month. Measured: **14
seconds just to read one workbook** on this desktop, with a 187MB process peak
against an 89MB pandas baseline. Correct the document when this ships.

- `api/requirements.txt` and `requirements.lock` stay in step.
- Memory: built to stay viable for 512MB, but the target for this work is local.

  record peak memory per stage in the job status. If stage 3's G2 and G4 builds
  prove too heavy for a later deployment, that is a finding, not a blocker now.

## 13. Timing, measured and estimated

| Item | Figure | Basis |
|---|---|---|
| Read one month | 14s | Measured here, `openpyxl` |
| Read 80 months once | about 19 minutes | 14s × 80, plus extraction, not measured |
| Full offline rebuild | 41 to 77+ minutes | Logs, with 2 reads; latest 3-read run stops at 35 minutes in phase 1 |
| Stages 2 to 7 | Unknown | Roster solve is 190s per seed offline for a much larger experiment. Measure in build |

So the full 80-month run is a 20 to 30 minute job at best (estimate). The demo
has two routes, both real and both supported:

- **Full:** all 81 raw files plus the rest.
- **Quick (recommended for showing people):** the four pure CSVs as history plus
  one to three raw months. The transformation still runs visibly, and the whole
  chain should finish in minutes, though stages 2 to 7 are not yet measured.

## 14. How we build it

**Isolation.** The live app stays on `main`. Work happens on branch
`feature/full-pipeline` in a git worktree at
`C:\Users\BIBINBUSINESS\healthforecast-pipeline`, outside OneDrive so `.venv` and
`node_modules` do not sync. Setup there needs `git submodule update --init
--recursive`, a new `api/.venv` from `requirements.lock` plus `openpyxl`, and a
copy of `api/.env`, which never gets committed. Only one copy runs at a time,
because both use ports 8000 and 5173.

**Order.** Each step leaves the app working.

1. Worktree, then `data_version` and invalidation, then section 8.2 fixes.
2. Demo pack, `ops_derive`, new slots, `publish`. Pages run on uploaded files.
3. Transformation port and the equivalence test. This is the riskiest step, so
   it comes before anything depends on it.
4. Job runner and stages 0 to 6.
5. Data Hub rework and tracker.
6. Consolidated table and new analyzers.
7. Stored recommendations, banners, data source note, AI provenance.
8. Full local demo on both routes.

## 15. Definition of done

- `npm run build` passes, `npx playwright test` passes with new routes and a rule
  that Data Hub fires no POST on load, and `api/tests` passes.
- Both demo routes run in a real browser against the running backend, by real
  file upload, with every stage green or knowingly amber.
- After a second run with changed data, needing only the changed file re-uploaded,
  each page and the assistant show the new numbers. A test asserts each `/last`
  payload carries the new `data_version`. The labelled thesis constants in the
  rostering ladder are the one stated exception.
- All 80 months match or differences are explained.
- A search of logs and responses from a real run finds no patient identifier.
- Peak memory and time per stage are recorded and reported, not assumed.
- Nothing is merged to `main` or deployed without Jonathan's approval.
